## 2. The TERM axis needed no bdump parser

Round 14 recorded that the term axis "needs the bdump parser, and landing two
solid axes beat landing three shaky ones". That was wrong in a cheap way:

```pascal
if wantTerm then
  Writeln('solvedterm ', h^.nperiods, ' last ',
          (h^.lastdate.y + 1900), '-', h^.lastdate.m, '-', h^.lastdate.d);
                                                 { amort_oracle.pas:1216 }
```

The `solvedterm` echo carries **both** cells DOS leaves the term solve in —
`h^.nperiods` and `h^.lastdate` — so a five-line field scan is the whole parser.
`bdump` is only needed when the balloon GRID is under test.

**Both cells are compared, not just the count.** A grid that is off by a period
can land on the right count with the wrong final date (the same reasoning
`dos_fuzzer5_test.go:1518` gives). The criterion:

- **count** — `|n_recovered − n_original|`, port must not exceed DOS's. There is
  no quantum: the term is an integer, and rounding the payment to the cent can
  legitimately push the loan one period past its original term, but it pushes
  DOS exactly as far as it pushes the port.
- **final date** — compared when the counts agree, against DOS's recovered date.

`noterm` (blank BOTH cells) is used rather than `non` (blank n, keep a typed last
date), because `non` hands the solver most of the answer back and needs explicit
`lastdmy=` on both sides. That is v3.

Standing gate, 60 cases (seed 1401):

```
term compared 60, port-worse 0, date-differs 0, both-drifted 13 (max port drift 1 period)
```

The thirteen "both-drifted" cases are DOS and the port landing one period past the
original term together — the payment quantum doing exactly what it should. They
are counted and logged rather than folded into the pass, so a run of them cannot
hide inside a green count.

## 3. Adjudicating round 14's long-horizon rate signal

Round 14 left this open with the confound stated precisely: 130-337 year terms
are §54/§55 territory, so "the solver under-converges" and "the port's dates are
not DOS's out there" were not separated.

**They separate cleanly, because §54 and §55 are not the same year.** From
`rtInput`'s fixed 2024-01-01 loan date:

| boundary | what | first bites |
|---|---|---|
| §54 | DOS tests `y mod 4`, so it believes 2100 IS a leap year | Feb 2100 — 76 years out |
| §55 | DOS's `daterec.y` is a Pascal BYTE; the calendar wraps mod 256 | 2155 — 131 years out |

`TestRoundTripRateHorizonStrata` draws four strata against those boundaries.
Pre-fix, seed 1501, 25 cases each:

| stratum | span | ends | port-worse |
|---|---|---|---|
| A | 2-40 yr | ≤2064 | 0 / 25 |
| **B** | **50-74 yr** | **≤2098** | **3 / 25**, worst 3830× |
| C | 80-125 yr | 2104+ | 6 / 22, worst 87566× |
| D | 140-320 yr | 2164+ | 1 / 3 |

**Stratum B is the whole experiment**, and it fails: spans ending 2095, 2096 and
2098 — short of BOTH boundaries. Whatever this is, it is not the calendar.

The matched-n control settles the other confound (horizon in years is entangled
with the period count at fixed `perYr`). Holding n fixed and varying `perYr`:

```
n=100 perYr=12 (ends 2032): 0/25 port-worse
n=100 perYr= 1 (ends 2124): 7/25 port-worse
n= 60 perYr= 1 (ends 2084): 0/25 port-worse
n=250 perYr=12 (ends 2044): 0/25 port-worse
```

Same solver, same iteration count, different calendar span. The failure follows
the span. It is not the iteration budget, and it is not the date layer.

Strata C and D are REPORTED, not asserted: they are known-broken calendar
territory and failing on them would re-report a decision Nate has already made.
A and B assert.

## 4. §57 — a Go-only pre-solve gating a DOS decision

Source audit first (standing rule 5), and it took one read. DOS's rate solve has
**no pre-solve at all**:

```pascal
function EstimateAndRefineRate: boolean;
begin with h^ do begin
  ...
  loanrate := payamt * peryr / amount;      {first guess - better high than low.}
  if (loanrate<0.02) then loanrate := 0.02; {Iterate won't work if you start with zero.}
  if Iterate(amount, usap, loandate, firstdate, loanrate, til_adj) then
    ...                                          { Amortize.pas:467-491 }
```

Seed, then `Iterate`, unconditionally. The port put a closed-form Newton loop
(`backward.go`, `const maxIter = 30`, a secant on the `RepayLoan` terminal
residual) in front of that, and made `dosIterateRate` reachable **only from
inside that loop's `math.Abs(step) < teeny` convergence branch**. When the port's
own pre-solve failed to settle in 30 iterations, `SolveRate` fell out of the loop
and returned the **unrefined closed-form estimate with `converged=false`** —
having never attempted the DOS `Iterate`.

The probe that nailed it: on the three failing screens, `dosIterateRate` called
directly returns DOS's answer to the last digit (2.66e-07, 6.84e-08, 1.00e-07 of
the entered rate) while `SolveRate` returns 2.24e-05, 1.91e-04, 3.85e-04 with
`converged=false`. **The refinement was correct all along and was never reached.**

**Where it is live:** loans deep into perpetuity territory, where the payment is
within a hair of `A·i` and the principal barely amortizes. The marker is the
perpetuity depth `(1+i)^-n`; every observed failure sits below 1e-5. There
`RepayLoan`'s terminal balance is astronomically stiff in the rate, the secant's
reused `delta` collapses into cancellation noise, and `|step|` never reaches
`teeny`.

**`SolveLoanAmount` does NOT have this shape** and is unaffected — checked, not
assumed: its estimate is a genuine closed form with no iteration, and it calls
`dosIterateAmount` unconditionally whenever `needScheduleRefine` says to
(backward.go:332). That asymmetry is why the amount axis was clean in every
stratum while the rate axis was not.

The user-visible effect is twofold: a rate wrong in the 4th-5th decimal place,
**and** a spurious "did not converge" warning on a screen DOS answers cleanly.

### The fix

After the loop exhausts `maxIter` — and **after** the existing ±200% refusal,
which DOS also applies (AMORTOP.pas:1485) — run `dosIterateRate` from the DOS
seed, exactly as DOS does, and accept the result under the same guards the
converged branch uses. Those guards moved into `acceptRefinedRate` so the two
paths cannot drift.

Post-fix, the same strata, same seed:

| stratum | port-worse | mean err Go vs DOS |
|---|---|---|
| A | 0 / 25 | 1.43e-07 vs 1.47e-07 |
| B | 0 / 25 | 1.27e-07 vs 1.29e-07 |
| C | 0 / 22 | 1.08e-07 vs 1.08e-07 |
| D | 0 / 3 | 2.27e-07 vs 2.27e-07 |

Every matched-n control row is 0/25 as well.

### The regression, and its honest limit

`zzratepresolve_test.go`, four tests, one per independent component, every golden
carrying its oracle command and output:

| component | test | revert signature |
|---|---|---|
| the post-loop fallback | `TestSec57PreSolveExhausted` | exactly the 3 §57 cases fail; other 3 tests stay green |
| inert on the converged branch | `TestSec57InertWherePreSolveConverges` | — |
| the ±200% refusal still fires | `TestSec57RefusalStillFires` | see below |
| a negative refined rate still accepted | `TestSec57NegativeRateStillAccepted` | — |

**The third component is not fully witnessed, and this is stated in the test
rather than papered over.** The fix places the fallback after the ±200% check,
but the test passes with the two SWAPPED — on that screen the DOS `Iterate` does
not return an in-range rate either, so the ordering is not observable. It
witnesses that the refusal still fires, not that the order is load-bearing.

That gap is itself the same shape as §57: **the port's ±200% refusal is triggered
by the PORT's pre-solve wandering out of range, whereas DOS's is triggered by
DOS's own `Iterate`.** A direct hunt (600 screens, seed 7701, payment drawn
independently of any forward solve at 0.05x-6x of `amount/n` — the only draw that
reaches a divergent rate solve) found:

```
drawn 600 | port refused 18 | DOS also refused all 18 | mismatches 0
```

Per standing rule 8, that bounds only what the draw reaches: rate held at 0.10, a
2024-01-01 loan date, whole-month frequencies, no advanced options — the fancy
`Iterate` path is untested by it. Recorded in `discrepancies.md` §57 as open, not
closed.

### Round 13's NEW=1 is NOT closed by §57 — the hypothesis was wrong

A third run went out specifically to settle START_HERE's outstanding gate #1:
`pre-§56 vs post-§57` on `44000-44039`. The hypothesis was that §57, being a
non-convergence fix, closes the `fz5NonConverge` advisory §56 shipped with. The
arithmetic supported it (the pre-§57 head carried 57 findings on that range and
the post-§57 head carries 56).

**It does not.** FIXED 1, STILL 55, NEW 1 — and the NEW is round 13's case,
unchanged:

```
amort_oracle 291207.99 0.1209560000 2688 24 exact prepaid
  loandmy=29.5.2024 firstdmy=29.7.2024 pts=0.009110 payhard=1962.94 norate bdump
```

Semi-monthly, `exact`, off the 15th anchor — **§56's region, not §57's.** The
one open item from §56's gate stays open, and START_HERE §2 says so.

This is the round's clearest illustration of standing rule 11. The inference was
reasonable, the arithmetic lined up, and it was wrong. Measuring it cost one run.

### And §57 shows up in the fuzzer corpus, from the other direction

The same run's FIXED case — recovered from the work files, see below — is:

```
amort_oracle 226197.89 0.1117370000 85 1 b365 prepaid r78 usa
  loandmy=6.8.2023 firstdmy=6.11.2023 mor=279
  pre=507:380:52:90.02 pre=543:5:1:1833.16
  adj=759:0.0237490000:33908.00 adj=795:0.0911720000:28289.15
  targ=2504.22 payhard=30049.30 norate bdump
```

**`norate` at `perYr=1` over `n=85` — an 85-year backward RATE solve.** That is
§57's signature exactly, found by a completely different instrument, on a screen
carrying a full advanced-option set rather than the plain loans the round-trip
gate draws. Nothing about the fuzzer corpus was chosen with §57 in mind, which
makes it the stronger of the two pieces of evidence.

The three sets are mutually consistent:

```
pre-§56   = {55 common} ∪ {the 85-year norate case §57 fixes}          = 56
post-§56  = {55 common} ∪ {85-year case} ∪ {§56's advisory}            = 57
post-§57  = {55 common} ∪ {§56's advisory}                             = 56
```

So §56 opened one and §57 closed a different one that predates both.

### Recovering the FIXED line, and the trap that nearly lost it

**`paired_regression.sh` deletes its work directory on exit** (`trap 'rm -rf
"$WORK"' EXIT`), so the counts survive in the log and the FIXED/NEW *lines* do
not. Round 15 hit this twice. The second time a 45-second watcher was copying
`$WORK/*.raw` aside — but the run finished inside a polling gap, so the snapshot
was truncated (a 56-line `post.raw` against a true 61) and a naive `comm` on it
reported **6** FIXED where the script reported **1**. Five of those six were
artifacts of the truncation.

The truncated set was thrown away rather than reasoned from, and a single POST
pass was re-run over the same 40 seeds to regenerate the set properly. It
reproduces the script's counts exactly. **A truncated set can only UNDER-report
NEW and OVER-report FIXED** — worth knowing, because the NEW line from the
truncated snapshot did match the script's printed regression and could have been
mistaken for a validated comparison.

### Cost note for the next session

Running two paired regressions concurrently on 2 cores roughly doubles each
one's wall clock (~60 min each pass rather than ~55 min total). It is still a
net win over serialising them, but budget ~2 hours per concurrent pair, and
**the container restarted mid-session at 16:20 UTC and killed the run that was
in flight** — its log was empty and it had to start over, losing an hour. The
filesystem survived intact (oracle, both trees, both binaries, the working
copy). Prefer starting the mandatory gate FIRST and alone.
